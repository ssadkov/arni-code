# Локальные автоматизации в Arni и Arni Code

Спецификация MVP для разработки · 2026-11-22

## 1. Результат

Пользователь один раз формулирует задачу в чате, проверяет результат и выбирает «Повторять по расписанию». Arni запускает её на этом компьютере в отдельной сессии, сохраняет результат в истории и, если включена доставка, отправляет краткую сводку в личный Telegram.

Пилот охватывает **Arni Code и Arni для Windows (`arni-lite`)**. Порядок разработки — сначала проверить существующий путь в Arni Code, затем добавить тот же сценарий в Arni. В `arni-backend` нужны привязка Telegram и доставка. Планирование, доступ к файлам и выполнение задачи остаются на устройстве. Серверное выполнение, синхронизация расписаний между устройствами, входящие триггеры, группы Telegram, вложения и email относятся к следующим этапам.

## 2. Сценарий в приложении

1. Пользователь выбирает «Повторять по расписанию» у своего запроса в чате или «Новая автоматизация» в списке задач. При создании из чата приложение подставляет исходный запрос, папку и модель. Форма позволяет их изменить. Для повторяемого запроса пользователь явно указывает всё, что нужно для выполнения, включая ссылки и имена файлов.
2. В форме есть название, запрос, модель, необязательная папка проекта, расписание и способ доставки. Расписание поддерживает «Ежедневно», «По будням» и «Еженедельно» с выбором дня недели. Рядом со временем показываются часовой пояс и ближайший запуск. Доставка по умолчанию — «Только в Arni».
3. Выбор Telegram открывает привязку, если её ещё нет. Перед сохранением форма показывает, что краткая сводка будет отправляться в выбранный личный чат. Пользователь подтверждает это сохранением задачи. Для задач с локальными источниками форма явно показывает, что сводка может содержать данные из выбранной папки.
4. В списке видны следующий запуск, последний результат и состояние доставки. Действия — «Запустить сейчас», «Пауза», «Изменить» и «Удалить». Ручной запуск использует тот же путь выполнения и выбранный способ доставки. При выбранном Telegram кнопка или подсказка у неё сообщает об отправке. Ручной запуск доступен на паузе и оставляет расписание на паузе.
5. История запуска открывает результат и показывает время, причину запуска, модель, статус выполнения и статус Telegram. Ошибка доставки видна отдельно от результата задачи.

Пример для приёмки в обоих клиентах — «По будням в 09:00 прочитай `status.md` из выбранной папки. Собери три пункта о том, что готово и что мешает продолжить. Пришли краткую сводку в Telegram». Тестовый файл содержит только специально подготовленные данные.

## 3. Фоновое выполнение

| Состояние | Поведение |
| --- | --- |
| Окно открыто или свёрнуто | Задачи выполняются по расписанию, пока пользовательская сессия ОС активна и устройство бодрствует. |
| Окно закрыто, фоновый режим включён | Задачи продолжают выполняться. Приложение остаётся доступным через трей. Настройка фонового режима включается явно. |
| Полный выход из приложения, выход из сессии ОС, сон или выключение | Выполнение возобновляется при следующем запуске приложения или пробуждении работающего процесса. Для каждой включённой задачи выполняется максимум один запуск за последнее пропущенное время, затем снова действует расписание. Устройство само не пробуждаем. |
| Пауза | Пропущенные во время паузы запуски не догоняются. Возобновление рассчитывает следующий запуск от момента включения. Пауза сохраняет уже запущенный прогон и его результат. |
| Перезапуск посреди выполнения | История показывает, что запуск прерван. Прежний набор инструментов автоматически не переигрывается. Если результат уже сохранён, допускается восстановить очередь доставки без вызова модели. |
| Нет сети, входа, модели, баланса или папки | Причина отображается в истории. Другую модель, аккаунт или папку приложение автоматически не выбирает. Пробный запуск и запуск по расписанию используют действующие тарифы и лимиты Arni. |

Задача закреплена за локальным профилем, установкой и аккаунтом Arni, под которым создана. Несколько окон одной установки не запускают её повторно. Выход из аккаунта останавливает автоматические запуски и доставку под этим аккаунтом. После входа другим пользователем задачи первого аккаунта недоступны. Одинаковые задачи, вручную созданные в двух клиентах, имеют независимые расписания.

## 4. Контракт выполнения

- **Задача.** Стабильный ID, владелец, название, исходный запрос, ID модели, папка проекта при наличии, расписание с часовым поясом, состояние и настройки доставки. При создании берём часовой пояс устройства и фиксируем его в задаче. Храним следующие расчётные времена в UTC. При переводе часов отсутствующее локальное время пропускаем, повторяющееся исполняем один раз.
- **Запуск.** Свой ID и неизменяемый снимок настроек, тип запуска `manual`, `schedule` или `catch_up`, запланированное время для автоматических запусков, времена старта и завершения, статус и ссылка на результат. Для автоматического запуска используем устойчивый ключ из ID задачи и запланированного локального слота в часовом поясе задачи. Планировщик атомарно резервирует слот. У одной задачи одновременно может выполняться только один прогон. Повторный клик возвращает активный прогон. Слот, пришедшийся на активный прогон, отмечается пропущенным.
- **Сессия.** Каждый прогон начинает отдельную сессию с сохранённым запросом. Смена выбранной папки или модели в обычном чате на неё не влияет. Используем существующие ограничения на число вызовов модели и инструментов, плюс таймаут запуска. Предлагаемый таймаут MVP — 10 минут.
- **Инструменты.** Фоновый профиль разрешает чтение из выбранной доверенной папки через штатные инструменты и обычный веб-поиск Arni. Без папки доступ к локальным файлам закрыт. Применяем ограничения путей, включая ссылки и junction. Запуск терминала, запись файлов, внешние действия и произвольный MCP в фоне недоступны. Если задача упёрлась в действие, требующее подтверждения, прогон завершается со статусом «Требуется внимание» и объяснением в истории. Обычный интерактивный запуск сохраняет свои правила подтверждений.
- **Результат.** Сначала записываем ответ и итог выполнения локально. Отдельно сохраняем состояние доставки `off`, `pending`, `sent`, `failed` или `unknown`. Изменение расписания применяется к будущим прогонам. Удаление задачи останавливает будущие запуски и отменяет ещё не отправленные сообщения, результат завершённой сессии остаётся в истории.

## 5. Telegram

**Привязка аккаунта.** Авторизованный клиент запрашивает короткоживущую одноразовую ссылку `t.me/<bot>?start=<token>`. Бэкенд хранит хеш токена, владельца и срок действия. Бот принимает `/start` только из личного чата. После получения события клиент показывает найденный аккаунт Telegram и просит подтвердить привязку. Погашение токена и подтверждение выполняются с проверкой владельца и срока. Один аккаунт Arni имеет одну активную привязку для обоих клиентов. Токен бота и числовой `chat_id` остаются на сервере. Отвязка отзывает привязку. Повторная привязка создаёт новый ID, старые задачи и ожидающие доставки требуют явного выбора нового получателя. [Telegram Deep Linking](https://core.telegram.org/bots/features#deep-linking)

**Доставка.** После успеха приложение автоматически ставит краткую сводку в очередь, если для задачи выбран Telegram. Формат — название задачи, время и короткий текст, максимум 3 000 символов в одном сообщении. При ошибке в задаче показываем ошибку в приложении. Для пилота требуется отправка только успешных результатов. Промпт, история чата целиком, файлы и вывод инструментов на endpoint доставки не передаются. Модель не получает токен, `chat_id` или инструмент отправки. Веб-страница или файл, обработанные во время запуска, не могут поменять получателя.

**Предлагаемые границы API.** Точные URL можно согласовать с разработчиком вместе с миграцией. Для клиентов нужны операции начать привязку, прочитать состояние, подтвердить, отвязать и отправить результат. Клиент передаёт в операцию доставки `runId`, `bindingId` и текст сводки. Сервер получает аккаунт из текущей авторизации и проверяет активную привязку этого аккаунта. Telegram webhook проверяет `X-Telegram-Bot-Api-Secret-Token` и повторную обработку одного `update_id`. В логах и телеметрии пишем технический статус без токенов, сводок и локальных путей. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook)

**Повторы.** Бэкенд атомарно резервирует доставку по `(userId, runId, bindingId)` до вызова Telegram. Повтор от клиента с тем же содержимым возвращает текущее состояние. С тем же ключом и другим содержимым возвращается конфликт. При подтверждённом `429` сервер сообщает `retry_after`, а клиент сохраняет сводку и повторяет запрос после этого интервала. Перед повторной отправкой сервер проверяет, что привязка ещё активна. Если Telegram мог принять сообщение, но ответ потерян, статус — «Доставка не подтверждена». Автоматически повторяем только попытки, для которых известно, что сообщение не принято. Для неопределённого статуса MVP показывает объяснение и сохраняет результат в истории. Повторы доставки не запускают LLM заново. [Telegram ResponseParameters](https://core.telegram.org/bots/api#responseparameters)

## 6. Точки интеграции и порядок работ

1. **Arni Code.** `product.json` задаёт `quality: stable`, а `automations.contribution.ts` отключает настройку по умолчанию для stable. Проверить запуск через `AgentHostAutomationService` с реальным агентом и моделью Arni. Хост уже держит каталог и историю, поддерживает cron с часовым поясом и догоняющий запуск. Использовать этот путь для MVP, включая ручной запуск и обработку завершения. Сверить правила пропусков и повтора локального часа с разделами 3 и 4. Проверить работу при закрытии последнего окна и привязать время жизни хоста к фоновому режиму приложения. Доставку привязать к сохранённому успешному прогону с учётом того, что renderer может быть закрыт.
2. **`arni-backend`.** Использовать существующую desktop Bearer-авторизацию. `src/lib/mediaAuth.ts` показывает проверку JWT и блокировки аккаунта, `src/lib/imageGeneration.ts` — существующее соглашение об идемпотентности. Добавить хранение привязок и попыток доставки, секрет бота, обработчик webhook и отправку. Подключить сначала отдельного тестового бота. Для задач и истории прогонов база на сервере в MVP не нужна.
3. **Arni для Windows.** Переиспользовать `AgentOrchestrator.RunAsync`, `ArniApiClient` и хранилища Arni Lite. Сейчас `ChatSession` связывает вызов модели и подтверждения инструментов с WPF. Вынести повторно используемые части исполнения в сервис, который можно вызвать в фоне с ограниченным набором инструментов. Сохранить текущую загрузку токена через `DpapiTokenStore` для пользователя Windows и механизм одного экземпляра приложения. Фоновый запуск должен работать на текущем .NET Framework 4.8. Проверка совместимости Windows 7 SP1 — отдельный прогон перед заявлением поддержки автоматизаций на этой версии.

Исходники Arni Code для старта — [настройка](../src/vs/sessions/contrib/automations/browser/automations.contribution.ts), [исполнение в Agent Host](../src/vs/platform/agentHost/node/agentHostAutomationService.ts), [формат расписания и триггеров](../src/vs/platform/agentHost/common/state/protocol/channels-automation/state.ts).

## 7. Критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Создание задачи из чата и из списка | Запрос, модель, папка, расписание и доставка сохраняются после перезапуска. Следующий запуск совпадает с выбранным временем и поясом. Пауза, правка и удаление работают из списка. |
| Реальный запуск в каждом клиенте | При закрытом окне и включённом фоновом режиме тестовая задача читает `status.md`. Результат доступен в истории, одна сводка доходит в привязанный Telegram. Для варианта «Только в Arni» запрос к Telegram не уходит. |
| Сон, полный выход, пауза | После пропуска нескольких слотов запускается максимум один догоняющий прогон. Период паузы не догоняется. При полном выходе до открытия приложения запуска нет. |
| Часовой пояс | Смена часового пояса устройства сохраняет расписание в исходном поясе задачи. При переводе часов повторившееся локальное время даёт один запуск, отсутствующее пропускается. |
| Дубли и перезапуск | Два окна, двойное нажатие и одновременный запуск по расписанию не создают параллельных прогонов одной задачи. После перезапуска прерванный прогон виден в истории, сохранённый результат повторно не генерируется. |
| Ограничения фонового профиля | Попытки выйти из папки, запустить команду, записать файл или сменить получателя не выполняются. Смена аккаунта закрывает доступ к задачам предыдущего пользователя. Отсутствие модели или исчерпание лимита отображаются как причины остановки. |
| Telegram и сбои доставки | Истёкшая либо использованная ссылка, чужой аккаунт, группа и отозванная привязка не проходят. Повтор одного запроса не дублирует сообщение. `429` и неопределённый результат показывают разные статусы. Старое сообщение не уходит в новый чат после перепривязки. |
| Регрессии | Обычный чат, подтверждения интерактивных инструментов, авторизация и биллинг работают в обоих клиентах как до интеграции. |

## 8. Оценка и открытые зависимости

- **Подтверждено по коду.** У Arni Code есть планировщик и исполнение в Agent Host. У Arni для Windows есть переиспользуемый цикл агента. Сервер уже принимает desktop Bearer-токены.
- **Оценка.** 1–2 инженерных дня на технический пилот в Arni Code с реальным прогоном и тестовой доставкой, если существующий путь работает с выбранной моделью Arni. Это оценка пилота. Оценку реализации фонового режима, общего бота и Arni для Windows уточнить после проверки.
- **Проверить в пилоте.** Совместимость выбранного провайдера Arni с фоновым профилем, время жизни Agent Host после закрытия окна, доступ к итоговому ответу из фонового процесса и сетевой доступ `arni-backend` к Telegram Bot API.
